# Employee Core Model Decision Pack

## 1. Purpose

This pack prepares the Product decisions for the future Employee core model. It does not approve a target model, define a backend DTO or database schema, or authorize implementation. Every “proposed target” is a recommendation for review unless its status is explicitly `APPROVED`; this document approves none.

Scope: PROD-02–PROD-12 and EMP-003–EMP-006. Documents, account provisioning, permissions, lifecycle workflow, Attendance, Leave, Payroll and Recruitment operations are referenced only where they constrain the core model.

## 3. Legacy Employee core model

The legacy core is `apps/hr/models.py:StaffProfile` with related `AddressDetails` and `BankAccount` records. It contains:

- Integer primary key; optional one-to-one User; optional self-supervisor MPTT relationship.
- Personal identity/contact: image, names, Aadhaar-name, gender, phone, personal/office email, DOB, marital status, blood group, social profiles and emergency contact.
- Employment: five-value status, Employee code, Branch, Department, Designation, Role, Holiday Master, Week Off, remote-clock flag, active flag, leave/sick allowances, start/end dates.
- Statutory: PAN, Aadhaar, PF/UAN/ESIC numbers and joining/exit dates.
- Two generic addresses and a generic bank record.
- Created/modified timestamps inherited from `administration.TimeStampedModel`.

Company is derived from the single optional Branch FK. Direct Employee create nevertheless requires a Branch and verifies its Company (`apps/hr/views.py:employee_create`). Department and Designation are nullable in the model but required by `apps/hr/services.py:create_employee`. Week Off and Holiday Master are optional. Shift exists as `ShiftMaster` but StaffProfile has no Shift FK. No assignment is effective-dated and no assignment-history model was found.

Employee code is generated by `apps/hr/views.py:generate_branch_emp_id`: status `4` uses `TEMP`; otherwise Branch `emp_id_series`; the next number is Company-wide max+1. `emp_id` is nullable, non-unique at database level, and later editable by `update_work_info`.

## 4. Current React Employee model

The React Zod form currently contains broad personal, two-address, employment, statutory, bank, emergency and document fields. `Employee` adds numeric `id`, required string `employee_id`, Candidate/Offer provenance, timestamps and `is_active`.

Core-model issues evidenced in source:

- `company`, `department`, `designation`, `reporting_manager`, `week_off` and `holiday_master` are strings or optional strings.
- Branch and Shift assignments do not exist.
- `work_location` is a required string independent of Company Branch.
- `employment_type` is required but does not map to legacy Staff status; legacy Temp is a status/code rule.
- `annual_salary` is required in Employee even though legacy salary is Payroll-linked rather than a StaffProfile field.
- Employee document fields are embedded in the main form schema even though documents have their own API lifecycle.
- React marks more personal/bank fields required and validates more strictly than legacy.
- Employee code is optional in the form, disabled in the UI, and generated by a mock sequence unrelated to Branch.

The Company module already exposes numeric frontend IDs: `Company.id`, `Branch.id/company_id/employee_id_series`, `Department.id/company_id`, `Designation.id/company_id/department_id`, `WeekOff.id/company_id`, and `HolidayList.id/company_id/year` (`frontend/src/modules/company/types/company.types.ts`). It has no Shift master.

## 5. Target Employee model proposal

The recommended target boundary is a normalized frontend domain model separated from create/edit form state and backend transport. This is a recommendation only:

- Use opaque entity identifiers for Employee and Company-owned relationships; with current Company source these are numeric frontend IDs, but final serialization is `BACKEND REQUIRED`.
- Store relationship IDs, not display labels. Resolve labels through Company-domain option queries/adapters.
- Keep core Employee scalar data separate from documents, account credentials, permission assignments, Attendance records, Leave balances and Payroll calculations.
- Preserve Candidate/Offer provenance only if Product approves it and Backend makes it immutable/system-controlled.
- Model lifecycle separately from employment classification; do not map `Temp` silently to React `employment_type`.
- Do not put Shift in the initial core model until Product assigns ownership and Attendance/scheduling provides a contract.
- Treat Week Off and Holiday List as candidate policy references, pending requiredness/effective-history decisions.
- Treat compensation as Payroll-owned or a privileged subresource unless Product explicitly approves it as Employee core.

This proposal cannot become implementation input until the questions in section 23 are answered.

### CORE-02 decision — legacy-parity create requiredness

**Decision status: RESOLVED for the legacy-parity baseline.** The target React Employee create form must initially preserve the demonstrated legacy creation contract. This decision does not define a backend DTO, approve modernized requiredness, or resolve field survival, editability, lifecycle, permissions, Employee-code policy, or related-module ownership.

Requiredness has three evidence levels:

1. **Server/service required** — the Django view or service explicitly rejects/looks up the value, or related-record persistence cannot succeed without it.

3. **Model required only** — the model declares a nonblank/non-null value but the workflow provides no dedicated validation. This is recorded separately and is not silently generalized.

#### Legacy creation-required fields

The legacy-parity baseline is:

- **Server/service enforced:** Branch, Department, Designation, both address Country/State/City references, and both persisted pincodes; PAN/Aadhaar are nonblank Staff model fields used by the create service.
- **Legacy UI enforced:** first name, last name, name as Aadhaar, personal email, phone, DOB, both address line 1 values, both Country/State/City/pincode groups, joining date, Branch, Department, Designation, five bank fields, and three emergency-contact fields.
- **UI-only anomaly:** reporting manager is marked required but its create-service assignment is commented out, so persistence parity is `LEGACY PARTIAL` rather than confirmed.
- **Status anomaly:** status is posted to a non-null Staff field but the UI permits an empty selection and has no required rule; the future representation remains Backend-owned.

#### Legacy model-required fields

- PAN and Aadhaar are nonblank/non-null StaffProfile CharFields and are supplied by the create service.
- Address name, Country, State, City, postcode, content type and object ID are non-null related-record fields. Address name and ownership metadata are supplied automatically; Country/State/City are resolved by the service; pincodes come from the form.
- Several non-null choice/string fields receive UI selections or defaults, but Django `objects.create()` does not call full model validation. Their choice validity must not be overstated.

#### Legacy creation-service-required fields

- `company_branch` is explicitly required by the service and the view.
- Permanent and correspondence Country/State/City are unconditional `get_object_or_404` lookups.
- Department and Designation are unconditional `get_object_or_404` lookups.

- B. Use a backend-generated Company/Branch sequence without tying Temp to lifecycle.
