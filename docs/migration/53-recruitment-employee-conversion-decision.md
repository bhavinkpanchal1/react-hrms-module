# Recruitment to Employee Conversion Decision

## 1. Status

CORE-10 is **PARTIALLY RESOLVED**. The legacy entry point, mapping, branch/code generation, Candidate state update and intended document copy are confirmed. Offer/Job involvement, provenance, idempotency, duplicate prevention, rollback safety and target authority remain Product/Backend decisions.

## 2. Legacy conversion entry point

The Recruitment Candidate list shows **Create Employee** only when `application_status == "Shortlist"` and interview `status == "Select"` (`templates/hr/recruitment/list.html:180-215`). Clicking opens a SweetAlert Branch selector and POSTs to `/recruitment/employee/create/<candidate_id>` (`apps/recruitment/urls.py:51`; template around lines 390-445). The view is `apps/recruitment/views.py:create_employee` at lines 600-681.

Required conversion input is the Candidate route ID plus an active Branch ID belonging to `request.company`. No Offer, Job, Department, Designation, manager, Role, Week Off, Holiday Master, joining date, bank, identity number, statutory field, salary or account input is requested. No explicit `HRResponsibility`/role check is demonstrated; Candidate itself is fetched by raw ID without validating `candidate.company` against `request.company`.

## 3. Confirmed legacy flow

1. Resolve Candidate by route ID.
2. Require Branch ID and validate that Branch is active and belongs to the active Company.
3. Generate Employee code from Branch with no Temp status input.
4. Create a minimal `StaffProfile`.
5. Optionally create one Permanent `AddressDetails` record.
6. Iterate CandidateDocument records and intend to create StaffDocument records.
7. Set Candidate `status="IsEmployee"`.
8. Return success.

This is creation of a **new Company-scoped Employee**. It is distinct from Company change, which closes Employee A and creates independent Employee B.

## 5. Candidate behavior

Candidate statuses are Pending, InScheduled, Reject, Select and IsEmployee (`apps/recruitment/models.py`). The UI exposes conversion only for shortlisted/selected Candidates. The view itself does not revalidate those statuses and can be called for any Candidate ID. Candidate becomes `IsEmployee` only after Staff/address/document operations. No `converted_to_employee` Boolean or Employee FK exists in legacy. Retry prevention relies only on UI status and is not enforced server-side.

## 6. Offer and Job involvement

Legacy conversion does not query an Offer or Job and does not update Offer state. Offer acceptance, offered salary and joining date are not prerequisites or mapping inputs. Candidate `position_applied` is free text and is not used to choose Department/Designation/Role. Therefore Offer and Job involvement is **NOT PRESENT** in the audited legacy conversion.

## 7. Employee creation and related resources

Conversion directly calls `StaffProfile.objects.create`, not HR `create_employee`; it creates a minimal Staff record and bypasses most CORE-02 fields. Branch is required and Company-validated. Code is generated from Branch without status, so ordinary Branch series is used. Status is omitted and the model default is Probation; `is_active` defaults true. No end date, correspondence address, bank, Department, Designation, account, Payroll or statutory resource is created.

Candidate documents are intended to produce StaffDocument rows. However, the call supplies `public=doc.public`, while audited `StaffDocument` has no `public` field. For a Candidate with documents this can raise an unexpected-keyword error before Candidate status update. Reusing the same storage field does not prove an independent physical copy; storage/reference behavior is backend-dependent.

## 8. Atomicity and rollback

The view has `@transaction.atomic`, so multiple database operations enter one transaction. However, its broad `try/except` catches exceptions **inside** the atomic boundary and returns JSON without re-raising or explicitly marking rollback. Django can therefore commit earlier successful writes for caught non-database errors. Classification: **multiple operations in a transaction wrapper, but rollback safety is not reliable**.

Consequences:

- Staff creation may succeed before address/document failure.
- Candidate status may remain unchanged while a Staff record exists.
- Some StaffDocument rows may exist before a later document fails.
- Retrying may create another Staff record/code.
- Branch validation failures occur before Staff creation and safely return no writes.
- Framework/database errors that mark the transaction broken may roll back, but this cannot be generalized to every caught exception.

Errors return the exception string with HTTP 500. No cleanup, reconciliation, retry token or recovery action is implemented.

## 9. Duplicate prevention

No durable Candidate→Staff link or unique Candidate/Offer provenance constraint exists. Conversion does not check Candidate status, existing Staff, email, phone, Aadhaar, PAN or prior conversion. `StaffProfile.email`, phone and Employee code are not demonstrated unique constraints. Candidate email/phone uniqueness applies only inside Candidate. UI hiding after `IsEmployee` is bypassable and fails under partial conversion. Duplicate prevention is **MISSING**.

## 10. Account, documents and Payroll

- Account/User, office email, password and portal access are not created. Account provisioning remains a later separate action and can change status to Regular.
- CandidateDocument→StaffDocument creation is intended for all categories, but has the `public` field mismatch and no ownership/security/versioning decisions.
- Salary, Payroll, CTC and salary history are not created. Candidate current/expected salary is ignored. Offer salary is not queried.
- No PF/UAN/ESIC values are created.

## 11. Permissions and tenant scope

The Candidate-list UI is in Recruitment and navigation may be controlled by `can_handle_recruitment`, but the conversion endpoint has no demonstrated flag/role/action check. Branch is correctly active-Company scoped. Candidate fetch, CandidateDocument query and Candidate status update are not explicitly Company-scoped. Target conversion requires a dedicated authorized capability and tenant validation for Candidate, Branch and every referenced master.

## 13. Proposed target flow

**Recommendation, not legacy parity:** one authorized backend conversion command:

`Candidate → lock/idempotency check → validate tenant/prerequisites and CORE-02 fields → resolve Company master IDs → create Company-scoped Employee with Probation status and Company code → optionally link/copy approved documents → persist immutable provenance → update Candidate and approved Offer state → commit → return one result`.

All required operations through Candidate/Employee/provenance state change must share one rollback boundary. Account provisioning should be a separately approved post-conversion workflow unless Product explicitly makes it part of the transaction. Payroll compensation remains Payroll-owned. Missing onboarding fields may require an HR completion form before committing rather than silently creating an incomplete Employee.

Recruitment conversion creates a new Company-scoped Employee and defaults its status to Probation without HR status selection. Company change closes Employee A and creates independent Employee B; it does not reuse a Person or Employee record. The commands, validation and provenance remain distinct.

## 15. Backend decisions

Define one atomic conversion service/transaction; Candidate/Offer/Job/Employment relationships; immutable provenance; tenant/master validation; row locking/idempotency key and unique constraints; Candidate/Offer state machine integration; field mapping and validation errors; code allocation; document copy/reference atomicity; rollback/reconciliation; authorization; audit actor/time/source; concurrency; and stable success/error response. No endpoint URL is approved.

## Approved conversion Product contract

- Direct HR Employee creation requires neither Candidate nor Offer; status defaults Probation with authorized HR choice of Probation/Regular/Temp.
- Recruitment conversion requires Candidate and accepted Offer, creates a new Company-scoped Employee with Probation, and creates neither Account nor Payroll.
- Candidate becomes Hired/Joined only after Employee creation succeeds and retains a reference to the created Employee; Candidate may retain Employee ID/code for traceability. Employee Detail may display read-only Recruitment Source, Candidate ID and Offer ID.
- If already converted, block duplicate creation, return/reference the existing Employee and allow authorized HR to open it.
- If Employee creation fails, Candidate remains in its pre-conversion state and no partial conversion commits.

Atomicity, locking/idempotency, provenance persistence, accepted-Offer validation, rollback/reconciliation, exact Candidate state representation and response/error contracts remain Backend-required. No endpoint is approved.

## 16. Legacy anomalies

- `@transaction.atomic` is undermined by catching exceptions inside the decorated function.
- StaffDocument creation passes nonexistent `public`, likely failing Candidates with documents.
- Candidate is not Company-validated while Branch is.
- UI prerequisites are not revalidated at the endpoint.
- No Candidate→Staff relation or duplicate constraint exists.
- Minimal conversion bypasses the main HR create service and CORE-02 breadth.
- Candidate gender strings do not match Staff single-character vocabulary.
- Marital “Other” collapses to Unmarried.
- Candidate documents may reuse the same storage field rather than create an independent blob.
- Offer, Job, salary, joining date, Department and Designation are ignored.
- Exception text is returned to the client.
